# cuLenia: документация проекта

## Назначение

`cuLenia` - это CUDA/C++ реализация Lenia с визуализацией через GLFW, OpenGL, GLEW и несколькими режимами вычисления на GPU. Проект ориентирован не на готовое пользовательское приложение, а на производительную исследовательскую основу: можно менять размер поля, временное разрешение, сцены, набор каналов, правила роста, форму ядер и способ вычисления свертки.

В репозитории нет внешнего менеджера зависимостей и нет CMake. Основной поддерживаемый сценарий - сборка в Microsoft Visual Studio 2022 через `Lenia.sln` и `Lenia.vcxproj`.

## Что реализовано

- Непрерывная клеточная система Lenia на квадратной тороидальной сетке.
- Одноканальная сцена `Orbium` и трехканальная сцена `Tessellatium`.
- Общая модель данных `LeniaWorld` для каналов, правил, ядер и двойной буферизации.
- CPU-режим `HostMode`, который работает как эталонная/инициализационная реализация.
- CUDA-режимы прямой пространственной свертки: с OpenGL interop и без него.
- CUDA FFT-режимы на базе cuFFT: FP32, FP64 и BF16/FP16-путь через `cufftXt`.
- Визуализация состояния через OpenGL: `glDrawPixels` или texture/PBO с CUDA-OpenGL interop.
- Горячие клавиши для переключения сцен, режимов, размера сетки, `T`, частоты рендера и batched FFT.

## Быстрый старт

### Требования

- Windows.
- Microsoft Visual Studio 2022 с C++ workload и toolset `v143`.
- CUDA Toolkit 12.3.
- GPU NVIDIA с поддержкой целевой архитектуры проекта `compute_80,sm_80`.
- GLFW 3.4.
- GLEW.
- Доступные для линковщика библиотеки: `cufft.lib`, `opengl32.lib`, `glew32.lib`, `glfw3_mt.lib`, `cudart_static.lib`.

### Сборка в Visual Studio

1. Откройте `Lenia.sln`.
2. Выберите платформу `x64`.
3. Для производительности используйте конфигурацию `Release|x64`.
4. Проверьте, что Visual Studio видит include/lib пути CUDA, GLFW и GLEW.
5. Соберите проект `Lenia`.
6. Запустите собранный исполняемый файл из Visual Studio или из каталога сборки.

Альтернативно, если `MSBuild` доступен в окружении Visual Studio:

```powershell
msbuild Lenia.sln /p:Configuration=Release /p:Platform=x64
```

## Модель Lenia в проекте

Lenia хранит состояние мира как набор каналов. Каждый канал - поле значений от `0` до `1` на квадратной сетке `size x size`. На каждом шаге к каналам применяются правила. Правило берет один канал-источник, сворачивает его с ядром, пропускает результат через функцию роста и добавляет вклад в канал-назначение.

Упрощенный шаг:

```text
for each rule:
    source = grid[source_channel]
    potential = convolution(source, kernel)
    growth = 2 * exp(-((potential - mu)^2) / sigma2) - 1
    accumulated[destination_channel] += weight * growth

for each channel:
    next = clamp(current + accumulated[channel] / T, 0, 1)
```

Сетка обрабатывается как тор. Индексы на границах заворачиваются обратно в поле, поэтому формы не упираются в край экрана.

## Основные структуры данных

### `Rule`

`Rule` описывает одно правило взаимодействия:

- `source` - индекс канала-источника;
- `destination` - индекс канала-назначения;
- `radius` - радиус ядра;
- `mu` - центр функции роста;
- `sigma2` - ширина функции роста, заранее преобразованная в `2 * sigma * sigma`;
- `weight` - вес вклада правила;
- `mu64`, `sigma264`, `weight64` - double-версии параметров для FP64;
- `mu16`, `sigma216`, `weight16` - BF16/BF162-версии параметров для FFT16.

Входные массивы правил в `main.cpp` имеют 11 чисел:

```text
source, destination, radius, relRadius, rank, alpha, beta0, beta1, mu, sigma, weight
```

Поля `relRadius`, `rank`, `alpha`, `beta0`, `beta1` используются только при генерации ядра. После генерации в `Rule` остаются параметры, нужные на шаге симуляции.

### `LeniaWorld`

`LeniaWorld` хранит:

- количество каналов `nbChannels`;
- количество правил `nbRules`;
- размер сетки `size`;
- временное разрешение `T`;
- флаг двойной буферизации `toGridB`;
- цвета каналов `color`;
- пороги случайной инициализации `threshold`;
- массивы правил `rule`;
- указатели на сетки `gridA` и `gridB`;
- указатели на ядра `kernel`;
- отдельные массивы для FP32, FP64 и BF16.

Лимиты заданы в `lenia.h`:

- `MAX_CHANNELS = 10`;
- `MAX_RULES = 20`;
- `MAX_RANK = 5`.

Если добавляется сцена с большим числом каналов, правил или рангов ядра, эти константы нужно увеличить и проверить массивы на host/device стороне.

## Инициализация

### Сцены

`main.cpp` содержит две сцены.

`Orbium`:

- 1 канал;
- 1 правило;
- зеленый рендер;
- `T = 16`;
- радиус правила `15`;
- начальный порог заполнения `0.2`.

`Tessellatium`:

- 3 канала: красный, зеленый, синий;
- 15 правил;
- `T = 8`;
- радиус правил `12`;
- межканальные и внутрикaнальные взаимодействия;
- начальный порог заполнения `0.5` для каждого канала.

### Host-first инициализация

Все device-режимы создают временный `HostMode`:

1. `HostMode` заполняет `LeniaWorld`.
2. Для каналов создаются случайные `gridA` и пустые `gridB`.
3. Для правил генерируются нормализованные ядра.
4. Device-режим копирует данные на GPU.
5. Временный `HostMode` удаляется.

Такой подход уменьшает дублирование кода и делает CPU-инициализацию общей для всех GPU-вариантов.

### Генерация ядра

`initKernel` создает квадратное ядро размера `(2R + 1) x (2R + 1)`. Для каждой точки:

1. вычисляется нормированное расстояние от центра;
2. если точка попадает в относительный радиус `relR`, используется `kernel_shell`;
3. значение умножается на соответствующий `beta`;
4. после заполнения ядро нормализуется на сумму всех значений.

Для прямой свертки ядро хранится компактно. Для FFT-режимов оно дополнительно разворачивается в сетку `size x size`, чтобы его можно было преобразовать через FFT и умножать в частотной области.

## Главный цикл выполнения

`main.cpp` выполняет:

1. `glfwInit`.
2. Создание окна `1024 x 1024`.
3. `glfwMakeContextCurrent`.
4. `glewInit`.
5. Регистрация callbacks.
6. Стартовый `toggle(window, DEVICE_FFT16_MODE)`.
7. Бесконечный цикл до закрытия окна:
   - увеличить счетчики FPS и рендера;
   - вызвать `mode->compute(renderCount == RENDER_UPDATE, batchFFT)`;
   - обновить заголовок окна через `checkFPS`;
   - если пора, вызвать `mode->render(w, h)` и `glfwSwapBuffers`;
   - обработать события через `glfwPollEvents`.

Заголовок окна показывает текущий режим, размер сетки, `T`, частоту рендера, состояние batched FFT, FPS и throughput в Mpx/s.

## Режимы вычислений

### `HostMode`

`HostMode` реализует CPU-версию вычислений:

- хранит host-массивы;
- выполняет прямую свертку по правилам;
- финализирует каналы и формирует `renderGrid`;
- рисует через `glDrawPixels`.

В текущем `main.cpp` этот режим не назначен на горячую клавишу. Практически он используется как общий инициализатор данных для GPU-режимов и может служить ориентиром для проверки алгоритма на CPU.

### `Device32noInteropMode`

FP32 CUDA-режим без CUDA-OpenGL interop:

- `gridA[i]`, `gridB[i]` и `kernel[i]` выделяются отдельно для каждого канала/правила;
- `leniaKernelnoInterop` считает шаг без подготовки пикселей;
- `leniaKernelRendernoInterop` считает шаг и пишет `float4` пиксели в device buffer;
- `render` копирует `cuPixels` в pinned host-память и вызывает `glDrawPixels`.

Этот режим полезен для сравнения стоимости GPU->CPU копирования с interop-режимом.

### `Device32Mode`

FP32 CUDA-режим с CUDA-OpenGL interop:

- вычисление такое же прямое, как в `Device32noInteropMode`;
- создается OpenGL Pixel Buffer Object;
- PBO регистрируется в CUDA через `cudaGraphicsGLRegisterBuffer`;
- render-kernel пишет `float4` пиксели напрямую в mapped PBO;
- OpenGL обновляет texture через `glTexSubImage2D` и рисует quad.

Этот режим убирает явную копию GPU->host при рендеринге.

### `DeviceFFT32Mode`

FP32 FFT-режим:

- все каналы хранятся последовательно в `lw.gridA[0]` и `lw.gridB[0]`;
- `lwFFT.sourceFFT` хранит FFT каналов;
- `lwFFT.kernelFFT` хранит FFT ядер;
- `lwFFT.destFFT` хранит произведения source FFT и kernel FFT по правилам;
- `lwFFT.dest` хранит результат обратного FFT для каждого правила;
- `convolveFFT32` перемножает комплексные спектры и делит на `size * size`;
- `computeLeniaStepFFT32` применяет функцию роста и обновляет каналы.

При `batchFFT = true` используются `cufftPlanMany` для всех каналов и правил. При `false` FFT запускаются в цикле по одному каналу/правилу.

### `DeviceFFT64Mode`

FP64 FFT-режим повторяет архитектуру `DeviceFFT32Mode`, но использует:

- `double`;
- `cufftDoubleComplex`;
- `CUFFT_D2Z`;
- `CUFFT_Z2D`;
- double-поля `Rule`.

Этот режим предназначен для проверки влияния точности, но обычно будет медленнее и потребует больше памяти.

### `DeviceFFT16Mode`

BF16/FP16 FFT-режим:

- использует `__nv_bfloat16` и `__nv_bfloat162`;
- FFT-планы создаются через `cufftXtMakePlanMany`;
- данные для обновления обрабатываются парами значений через `__nv_bfloat162`;
- `__hfma2_sat` одновременно выполняет fused multiply-add и saturation в диапазон `0..1`;
- `DIM = 16`, а `dimGrid2` уменьшает одну координату, потому что один thread работает с парой ячеек.

Это стартовый режим приложения. Он рассчитан на современные GPU с поддержкой BF16 и на целевую архитектуру `sm_80`.

## Прямая свертка против FFT

Прямая свертка:

- проще;
- хорошо подходит для малых радиусов и отладки;
- стоимость растет с площадью ядра и числом правил;
- в коде использует симметрию ядра, чтобы уменьшить количество операций.

FFT-свертка:

- требует больше служебной памяти;
- требует предварительного FFT ядер;
- обычно выгоднее на больших сетках и/или большом числе правил;
- естественно поддерживает batched выполнение через cuFFT;
- требует аккуратного хранения каналов и правил в последовательных массивах.

## Память и двойная буферизация

Проект использует `gridA` и `gridB` как ping-pong buffers:

- если `toGridB == true`, читается `gridA`, пишется `gridB`;
- если `toGridB == false`, читается `gridB`, пишется `gridA`;
- после шага `toGridB` переключается.

В direct-режимах массивы каждого канала выделяются отдельно:

```text
gridA[0] -> channel 0
gridA[1] -> channel 1
...
```

В FFT-режимах каналы лежат подряд в одном массиве:

```text
gridA[0] -> [channel 0][channel 1][channel 2]...
```

Такой layout нужен для `cufftPlanMany` и уменьшает количество отдельных аллокаций.

## Рендеринг

Есть два пути рендера:

1. CPU/host path:
   - GPU пишет `float4` пиксели в device buffer;
   - данные копируются в pinned host-память;
   - OpenGL рисует через `glDrawPixels`.

2. CUDA-OpenGL interop path:
   - OpenGL создает PBO и texture;
   - CUDA регистрирует PBO;
   - render-kernel пишет пиксели в mapped buffer;
   - OpenGL обновляет texture и рисует quad.

`RENDER_UPDATE` отделяет скорость симуляции от скорости отображения. При больших значениях симуляция делает больше compute-шагов между кадрами, что полезно для измерения throughput.

4. Создать host-инициализацию через `HostMode` или собственный загрузчик.
5. Добавить include в `main.cpp`.
6. Добавить константу режима.
7. Добавить создание режима в сценах.

### Изменить параметры Lenia

- `T` управляет размером временного шага: вклад роста делится на `T`.
- `radius` управляет радиусом ядра.
- `relRadius` ограничивает активную часть ядра.
- `rank` и `beta` описывают кольца ядра.
- `alpha` задает форму core-функции.
- `mu` и `sigma` управляют функцией роста.
- `weight` задает вклад правила в канал-назначение.

## Производительность

На производительность сильнее всего влияют:

- размер сетки `SIZE`;
- число каналов;
- число правил;
- радиус правил в direct-режимах;
- режим вычислений;
- значение `RENDER_UPDATE`;
- batched FFT;
- конфигурация `Release` против `Debug`;
- соответствие `CodeGeneration` реальной архитектуре GPU.

Практические рекомендации:

- для больших сеток начинайте с `DeviceFFT16Mode` или `DeviceFFT32Mode`;
- для проверки точности сравнивайте `DeviceFFT32Mode` и `DeviceFFT64Mode`;
- для оценки стоимости рендера сравнивайте `Device32Mode` и `Device32noInteropMode`;
- увеличивайте `RENDER_UPDATE`, если нужно измерить compute throughput;
- оставляйте `batchFFT = true`, если нет цели сравнивать batched и одиночные планы.

## Известные ограничения и риски кода

- Проект жестко привязан к Visual Studio, CUDA 12.3 и `sm_80` в `Lenia.vcxproj`.
- GLFW и GLEW не поставляются вместе с репозиторием.
- Автоматических тестов и benchmark scripts нет.
- Ошибки cuFFT, CUDA kernel launches и OpenGL interop проверяются не полностью.
- `checkCudaErrors` вызывает `system("pause")`, поэтому обработка ошибок Windows-specific.
- `HostMode` не доступен из горячих клавиш, хотя реализует `Mode`.
- При завершении `main.cpp` вызывает `toggle(window, 0)`. Эта функция удаляет текущий `mode`, затем вызывает `initLenia` с неизвестным режимом `0`; в `initLenia` после этого используется `mode->lw`. Это выглядит как потенциальный use-after-free на выходе.
- В `DeviceFFT64Mode.cu` в double-kernel update используется `expf`, хотя для FP64 ожидаемым выбором был бы `exp`.
- В `Device32Mode.h` и `Device32noInteropMode.h` есть повторный `#pragma once` в конце файла.
- Генерация случайного состояния использует `srand(time(NULL))`; для воспроизводимых экспериментов нужен фиксированный seed.
- `MAX_CHANNELS`, `MAX_RULES` и `MAX_RANK` ограничивают размер сцен статическими массивами.

## Ручная проверка после изменений

Минимальная проверка:

1. Собрать `Release|x64`.
2. Запустить приложение.
3. Проверить стартовую сцену `Tessellatium` в `GPU-FFT16`.
4. Нажать `1`, `2`, `3`, `4`, `5` и убедиться, что режимы переключаются.
5. Нажать `O` и `T` для переключения сцен.
6. Проверить `Up/Down`, `Left/Right`, `R/F`, `B`, `Enter`.
7. Наблюдать FPS и throughput в заголовке окна.

Для диагностики GPU:

- запускать Debug-сборку с CUDA error checking;
- добавлять `cudaGetLastError` и `cudaDeviceSynchronize` после kernels при отладке;
- проверять коды возврата cuFFT calls;
- сравнивать small-size результаты direct/FFT режимов с `HostMode`.
